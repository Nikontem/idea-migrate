# Build log: idea-migrate

This document is the decision record for building `idea-migrate`, a macOS
command-line tool that moves a JetBrains IDE project directory (IntelliJ
IDEA, PyCharm, WebStorm, GoLand, DataGrip) to a new location on disk and then
repairs the path references those IDEs keep in their own configuration
files, so the "Recent Projects" list and per-project settings keep working
after the move. A plain move in the Finder or with `mv` does not do this:
JetBrains IDEs store each project's absolute path in configuration files
outside the project itself, and those files are never updated by an
ordinary file move. The tool also makes a non-deleting backup of everything
it touches before it changes anything, and ships a matching undo path, so a
migration can be reversed even if the tool itself is what went wrong.

The work was carried out as 15 separate tasks, each implemented and then
independently reviewed before the next began. This log keeps the decisions
made along the way and the defects the reviews caught; the day-to-day
task-by-task mechanics of who implemented what and when have been left out
here in favor of what changed and why, which is what matters to a reader
returning to this project later.

## What was built

The tool is a single Python command-line program with a small internal
pipeline. It scans a JetBrains configuration root to find the installed
products and their stored recent-project lists, validates a requested move
(refusing moves into a directory's own descendant, refusing same-directory
moves, checking free space and filesystem boundaries), checks that no
JetBrains IDE process is currently running (so it is not rewriting
configuration a running IDE could overwrite on quit), and only then backs
up the affected configuration files, moves the project directory, and
rewrites the stored path references. Every migration writes a manifest
describing what it did and where the backup lives, and generates an
`undo.sh` recovery script that does not depend on the Python tool being
available or working. A separate command lists and restores from previous
backups. The whole thing is covered by roughly 160 automated tests by the
end of the build, including a full migrate-then-undo round trip that
replays the tool end to end against a disposable fixture project.

## The decisions that shaped the tool

**Validating a move.** The original design compared source and destination
paths as lowercased strings to detect a no-op "move to the same place."
That is not filesystem truth: on a case-sensitive disk it would wrongly
reject two genuinely different directories, and it did not understand `..`
in a path. It was replaced with a check that only treats a destination as
identical to the source when it already exists on disk and `samefile`
confirms it is the same inode. The check that rejects moving a directory
into its own descendant was also reordered to run before the check that
requires the destination's parent to exist, so a user seeing an error gets
the more specific and useful message. Separately, the tool deliberately
does not resolve symbolic links when it makes source and destination paths
absolute — it preserves whatever spelling the user typed, because the IDE
config files store the path text the project was actually opened under. If
a project was opened through a symlink whose target path is what the IDE
recorded, the rewrite step will not find a match for the un-resolved
spelling and the tool reports the surviving references rather than failing
silently; this was accepted as the right trade-off since a resolved path
would not match what is actually stored on disk.

**Detecting whether a JetBrains IDE is running.** The tool refuses to touch
configuration files while an IDE might have that same configuration open in
memory, because it could later overwrite the rewrite when it quits. Given
that the check works by matching process names, there is a theoretical false
positive — some unrelated program literally named, say, `idea` — but it was
judged unlikely enough, and easy enough for a user to clear by quitting the
offending process, that no bypass flag was added. Adding a `--skip-ide-check`
override was rejected outright: it would let anyone disable the one check
that exists to prevent silent configuration corruption, which is a far worse
failure than an occasional spurious refusal.

**Rewriting the path references inside IDE config files.** Early on, a
prescribed fix to the text-matching rule (to also treat whitespace as a
valid boundary after a path, so a path sitting at the end of an XML text
node would still be recognized) turned out to be unsafe, and is covered in
the defects section below since a reviewer caught it as a live corruption
bug. On a smaller point, when the code encounters a config file it cannot
parse, the decision was to log a warning via the standard Python `logging`
module rather than change any function's return type to carry a list of
skipped files — a return-type change would have rippled into the manifest
format and the final command-line report, while a log line does not. The
temp-file-then-atomic-rename write pattern used for rewritten config files
was later found to leave a stray temp file behind if the rename step itself
fails; that gap was accepted for this file (durability under a rare failure,
not data corruption) but is flagged below because the same gap was found and
fixed in a different file.

**Backups and the manifest.** The manifest is the single file that records
what the tool changed and where the backup lives, so `undo` and the
"list backups" command both depend on it being trustworthy. Its write was
changed from an in-place text write to the same temp-file-plus-atomic-rename
pattern already used elsewhere, specifically so a crash mid-write cannot
leave a truncated, unreadable manifest exactly when the safety net is
needed. A schema-version field was added to the manifest for future-proofing
but is not yet checked against on read; that was accepted for now since
there is no requirement yet to support old manifests written by an older
version of the tool. When a backup's manifest cannot be parsed at all (for
example if it is corrupted), the tool skips it in the "list backups" output
but now also logs a warning naming the directory, rather than making that
backup invisible with no explanation — silently hiding the one backup a
user most needs to find would defeat the point of listing backups.

**Restoring configuration on undo.** Undo restores backed-up config files by
merging them into the current configuration directory rather than wiping the
directory and replacing it byte-for-byte. This follows a deliberate design
principle carried through the whole build: the tool never deletes anything
it did not itself create. A wipe-and-replace undo would silently discard any
settings the user changed in the IDE between the migration and the undo — for
example, someone who migrated, used the IDE for a week, and then undid the
migration would lose that week's settings changes. The cost is that a
restored configuration directory can be left with a stale "recent project"
entry pointing at the now-vacated path; JetBrains IDEs tolerate a missing
recent-project entry gracefully, so this was accepted as a cosmetic issue the
user can clear from the IDE's own welcome screen. Related to this, the flag
that marks a backup as "undone" is deliberately only set after the restore
completes fully — if the restore fails partway through, leaving it unset
correctly signals "not fully undone, safe to retry" rather than claiming a
success that did not happen, and a retry safely declines to re-move a
directory that already exists in its restored location instead of
attempting the move again.

**Command-line reporting and failure handling.** Several fixes went into
making sure the tool never leaves a user in the dark or crashes with a raw
traceback where a plain error message would do: unhandled `OSError`s from
filesystem operations, keyboard interrupts, and end-of-input on a prompt are
all now caught and reported in plain language rather than as stack traces.
The most significant version of this problem is described in the defects
section below (a crash after the directory had already moved could leave the
user with no idea a backup even existed) — the fix makes the "your backup is
at this path, here is how to undo" message a function of whether the move
actually happened on disk, not of which exception class was raised, so it
prints correctly regardless of what specifically went wrong afterward. A
related, narrower fix: the tool was catching both `Ctrl-C` and end-of-input
at an interactive prompt the same way, which meant a user cancelling with
`Ctrl-C` saw a confusing "no input available, pass flags explicitly" message
instead of a clean cancellation — the fix narrows that catch to end-of-input
only and lets `Ctrl-C` propagate to the cancellation handling that already
existed. A separate bug meant `--dry-run` was silently ignored when combined
with the `undo` subcommand, so `idea-migrate --dry-run undo /path` performed
a real, irreversible undo while claiming to only preview it; that was fixed
so `--dry-run` is honored everywhere it is accepted.

**Scheduling the work.** Procedurally, reviews of one task were run at the
same time as implementation of the next task whenever the interfaces between
them were independent, to avoid 15 fully sequential round trips; the one
refinement made along the way was that a *fix* for a task already in review
counts as active implementation work and was never run in parallel with
another task's implementation, to avoid two people editing the tree at once.

## The serious defects that were found and fixed

Four defects stand out because each one would have caused real, hard-to-detect
damage to a user's data or IDE configuration if it had shipped.

**A directory could be moved into itself through a symbolic link.** The
check meant to stop a user from moving a directory into its own descendant
(which would either fail confusingly or, worse, recurse into itself) worked
by walking the plain, unresolved parent chain of the destination path. If a
directory *inside* the source tree was actually a symbolic link whose target
pointed back into the source tree, that lexical walk would not see the
loop, and the containment check would pass when it should have refused the
move. The only thing stopping disaster at that point was the operating
system itself — and that backstop does not exist on the tool's own
cross-filesystem copy path, where an unblocked case like this becomes a
directory recursively copying into itself. The fix resolves the real
(symlink-following) path before doing the containment check.

**A safety rule for rewriting file paths could corrupt an unrelated
directory whose name differed only by a trailing space.** The path-matching
logic needs a rule for "where does the path text end" — matching too
loosely means a path like `/Users/tester/Projects` would also match inside
`/Users/tester/Projects 2024`, silently corrupting a reference to a
completely different, untouched directory. An earlier fix had widened that
end-of-path rule to also accept whitespace, on the reasoning that
whitespace could never legitimately continue a path. That reasoning was
wrong: a space is a completely legal character in a macOS directory name.
A reviewer proved it by reproducing exactly the corruption the boundary
rule exists to prevent — moving `~/Projects` caused the tool to also rewrite
`/Users/tester/Projects 2024/x` into `/Users/tester/Moved 2024/x`, mangling
a sibling directory that was never supposed to be touched. The fix narrowed
the end-of-path rule to an explicit, non-whitespace set of characters. A
closely related, narrower version of the same bug was then found for the
`>` character (legal in a macOS filename, but never required to be escaped
inside these particular XML files) and fixed the same way.

**Verifying a cross-filesystem move could pass on an incomplete copy and then
delete the original.** When source and destination are on different
filesystems, the tool cannot use an atomic in-place rename; it has to copy
the project tree to the new location, verify the copy, and only then delete
the original. The verification step originally just checked that the
destination directory existed. But `shutil.copytree` creates that top-level
destination directory *before* it copies any of the files inside it — so
the check would report success for a copy that was arbitrarily incomplete,
for example one that failed partway through because a disk filled up or a
permission was denied. The very next step was to delete the source, which
would have meant losing the only good copy of the user's projects. The fix
walks both the source and destination trees and compares the full set of
relative paths together with each file's size (using the lower-level
symlink-aware `lstat`, so that symbolic links are compared as links rather
than by following them), and only deletes the source once everything
matches.

**The recovery script's "is an IDE running" check was wrong three separate
times in three different ways.** `undo.sh` is the last-resort recovery path
— it has to work even if the Python tool itself is what broke, so it is
plain shell and checks independently whether a JetBrains IDE is currently
running before it will restore anything. The first version used a broad
substring match against running process names, on the reasoning that a
false refusal is a safe failure. A reviewer disproved that on the actual
build machine: the pattern matched JetBrains Toolbox and a background
JetBrains daemon process, both of which start automatically, so `undo.sh`
refused to run essentially always — and every place the tool tells a user
how to recover points at this script. A safe-looking failure that blocks
the only recovery route is not actually safe. The fix narrowed the pattern
to match only the IDE launcher processes themselves. That fix then turned
out to be wrong in its own way: it used `pgrep -f`, which matches a
process's entire command line including its arguments, and the narrowed
pattern only matched a command line with no arguments — so it missed both
the actual background daemon (which runs with an argument) and how
JetBrains Toolbox actually launches an IDE (with a wrapped command line).
This version was worse than the first bug: instead of refusing to run, it
would restore configuration files while an IDE was genuinely open, and the
running IDE would then overwrite that restored configuration with its own
in-memory state on quit — silently discarding the rollback, on the one code
path that exists specifically for when something has already gone wrong.
The fix switched to matching against the bare process command name (which
strips arguments), mirroring the same technique the Python tool already
used elsewhere. Even that fix needed one more correction: the shell script
combines `set -e` with pipefail, and piping a large process list into
`grep -q` (which exits as soon as it finds a match, while the upstream
command is still writing) triggered a broken pipe in the upstream command;
under pipefail that made the whole pipeline report a nonzero exit even when
the pattern *did* match, inverting the check yet again. The final version
captures the process list into a variable first and tests the string,
avoiding the pipe entirely. A generated `undo.sh` was then run end to end
against a disposable home directory with both the background daemon and
Toolbox running, and it completed successfully — the exact scenario the
first two bugs had broken.

One more serious bug surfaced in the final whole-project review, close in
spirit to the ones above: the path-rewriting logic drops the
`$USER_HOME$`-style path variant when a migration's destination is outside
the user's home directory, which meant moving projects onto an external
drive would silently rewrite nothing and still report success, because the
reference-counting logic used the same incomplete variant list. This was
fixed even though it did not affect the specific migration this build was
tested against, since "move my projects to an external drive" is an
ordinary thing to want and a confident false success is a bad failure mode.

## What is still outstanding

A number of minor issues were deliberately deferred rather than fixed, on
the judgment that they were not worth the complexity or were not reachable
in realistic use. The main ones, grouped by area:

- **Configuration loading.** Loading the config silently falls back to
  defaults if the config path exists but is not a regular file, with no
  message explaining why the file was ignored. A related test only checks
  that some exception is raised when the config is frozen, rather than the
  specific error type, and there is no test for overriding the JetBrains
  root path specifically (the other two config fields are covered).
- **Product discovery and IDE matching.** Resolving a symlinked product
  directory could rename it inconsistently with an earlier filename check;
  this was judged unrealistic for how JetBrains stores its per-product
  configuration directories.
- **Race conditions and durability, not correctness.** The backup
  directory-naming logic has a narrow window where two simultaneous runs of
  the tool could both decide a directory name is free and then have the
  second one fail with an unhandled error — it fails safely (crashing rather
  than silently overwriting) rather than causing data loss. Separately, the
  parent directory of a rewritten config file is never explicitly flushed to
  disk after the atomic rename that writes it; the write itself cannot be
  torn, so this is a durability nicety rather than a correctness gap.
- **Test coverage gaps that are believed harmless.** A frozen data class
  used for the manifest holds list and dictionary fields, which means Python
  would raise an error if anything ever tried to hash it or use it as a
  dictionary key or set member — nothing in the tool does that today, but it
  is worth remembering if that class is extended later. A manifest
  schema-version field exists but is never checked on read. A sort used when
  listing backups by recency is a plain string sort and would misorder
  backups made ten or more times within the same second, which is not a
  realistic usage pattern.
- **Cosmetic and reporting nits.** When a migration finds and repairs zero
  path references, the report text ("Repaired 0 path references in 0
  files") does not distinguish "nothing needed fixing" from "the tool failed
  to find anything to check" — genuinely ambiguous wording worth improving.
  The `->` arrow lines in the plan and result summaries do not visually
  align because they sit under labels of different width. A generated
  `undo.sh` script accepts a broad substring match for a JetBrains-related
  process as a matter of policy (biasing toward refusing over destroying),
  which can in principle be triggered by an unrelated process whose name
  happens to mention JetBrains.

Alongside those, the round-trip test that exercises a full migrate-then-undo
cycle against a live fixture — the closest thing this project has to a
final, end-to-end verification — surfaced four findings of its own worth
recording. One (asserting that a file's permission bits are correctly
restored *between* the migration and the undo, not only checked after) was
promoted into the final fix wave and addressed. The other three were left
as-is: an assertion meant to catch cross-directory corruption of an
unrelated sibling folder is inert, since no plausible bug would share a
path prefix with it, so it should not be counted as real coverage; only a
failure of the final atomic-rename step is simulated for manifest-write
safety, while a failure during the earlier write-and-flush step is covered
only by the surrounding code structure, not by an actual test that
exercises it; and the round trip test never runs `undo.sh` itself (it uses
the tool's own Python undo path) — this was confirmed to be fine rather
than a gap, since a separate set of behavioral tests already runs the
shell script directly.

One item mentioned only cryptically in the source notes — a passing remark
about a test-helper's constructor and an unspecified default value — was
too underspecified to reconstruct with confidence and has been left out
rather than guessed at.
